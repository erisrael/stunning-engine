## 3. How a request flows

A payment from request to fulfillment, as built in `apps/api/src/operations.ts`, `apps/worker/src/stages.ts` and `database/001_initial.sql` onward.

| Step | Who | What happens | Code |
| --- | --- | --- | --- |
| 1 | Integrating backend | `POST /v1/payment-requests` with a server key. The request records items, currency, expected amounts, deadline and the environment of the key. It freezes the receiving accounts it may be paid into | `operations.ts`, migration 007 |
| 2 | API | Returns a submission token (`tvs_...`, HMAC-SHA256, scopes `submit` and `status`, 15 minutes by default) for the payer | `auth.ts` |
| 3 | Payer | Opens `/pay/` or the SDK widget. For a file, `POST .../uploads` reserves an upload; the file goes to private storage (signed ticket on local disk, or S3) | `packages/storage`, migration 002 |
| 4 | Payer | `POST .../submissions` with the upload, a QR text, a link or a reference. The submission and its first job are written in one transaction | `operations.ts` |
| 5 | Worker `extract` | Reads a QR, a provider link or a PDF text layer. Image-only receipts go to the `ocr` stage | `stages.ts`, `packages/evidence` |
| 6 | Worker `ocr` | Bounded Tesseract run (`WORKER_OCR_CONCURRENCY`, `OCR_TIMEOUT_MS`) | `tesseract.ts` |
| 7 | Worker `provider` | Leases the job, spends the provider budget, calls the connector (official receipt page, merchant API or a relay), records an observation | `stages.ts`, `reading.ts`, `link-connector.ts` |
| 8 | Database | `accept_payment` checks recipient, amount, currency, date, reuse and request state, then writes the acceptance, allocations and an outbox event in one transaction. A stale lease token discards the result | migrations 001, 024 |
| 9 | Worker outbox | Creates deliveries and posts signed webhooks (`x-verify-signature`, `x-verify-timestamp`, `x-verify-key-id`), retrying after 30 s, 2, 10, 30 minutes, 2, 6, 12 and 24 hours | `delivery.ts`, `egress.ts` |
| 10 | Integrating backend | Verifies the signature (SDK), applies the business action once per event ID, and reports it with `PUT .../fulfillment/{action}` | `packages/sdk-server` |

Results that are not a clear accept go to pending retries (`PROVIDER_RETRY_SCHEDULE`, default 1, 5, 15 and 60 minutes), to the review queue, or to a rejection with a reason code. The console's cashier, review decisions and batches reuse the same path.

## 4. Database and migrations

- **Engine.** PostgreSQL 17, UTF-8. Production runs in the `tv-postgres` container with the volume `transactionverify_pgdata`, never published on the server address.
- **Migrations.** `database/NNN_name.sql`, applied in order by `packages/persistence/src/migrate.ts` (`npm run db:migrate`, or the `tv-migrate` container on deploy). The runner takes a PostgreSQL advisory lock, records each file with a checksum in `public.tv_schema_migrations`, and runs each file in one transaction. A file may only use one outer `BEGIN; ... COMMIT;` pair.
- **Forward only.** Migrations only add. A changed checksum of an applied file is an error (see commit `6089c3f`, which restored the exact checksum of migration 041).
- **Generated parts.** Bank and wallet templates in migrations 016, 021, 027, 031, 048, 062 and 065 are generated from `packages/provider-connectors/src/drafts.ts` by `scripts/generate-method-drafts.mjs`. Do not edit them by hand.
- **Model check.** `database/verify_model.sql` exercises the core functions with synthetic data and rolls back. CI runs it.
- **Tenant wall.** Migration 013 adds row-level security on every table with `organization_id` (policy `tenant_wall`). `withTenant` sets `verify.organization_id` and switches to the role `verify_tenant`, because the deployment user is usually a superuser. The migration needs a user that may create roles.
- **Core functions.** `accept_payment`, `lease_verification_job`, `reserve_rate_limit`, `record_adjustment`, `refresh_method_draft`.

## 5. Authentication and permissions

| Caller | How it proves itself | Where |
| --- | --- | --- |
| Integrating backend | Server key `tvk_test_...` or `tvk_live_...` as a bearer token. Only the SHA-256 digest is stored. Test keys reach only the sandbox bank | `apps/api/src/auth.ts`, `packages/persistence/src/api-keys.ts` |
| Payer | Submission token `tvs_...` for one request, signed with `SUBMISSION_TOKEN_SECRET` | `auth.ts` |
| Staff | Cookie session (HttpOnly, SameSite=Strict, Path `/console`). Every console call needs `X-Console: 1` and a matching Origin. Passwords use scrypt; two-step codes follow RFC 6238; recovery codes; passkeys (WebAuthn, user verification required); remembered devices (default 30 days, 0 to 90) | `console/routes.ts`, `security.ts`, `passkeys.ts` |
| Staff with single sign-on | OpenID Connect authorization code flow with PKCE, for Enterprise organizations (flag `sso`). No accounts are created on sign-in | `console/sso.ts`, migration 033 |
| Cashier terminal | A device cookie binds sessions to cashier pages only, signs out after 15 idle minutes | migration 017, `console/cashier.ts` |
| Shopper | Cookie `tv_shop` (digest stored). Phone or email with password, Google (`GOOGLE_CLIENT_ID`), or Telegram | migration 059, `console/shop.ts` |
| Relay | Relay token per organization, used on `/relay/jobs` | `apps/api/src/relay.ts`, migration 053 |
| Telegram | `X-Telegram-Bot-Api-Secret-Token` checked against the stored webhook secret | `console/storefront-telegram.ts` |
| Outside monitor | Bearer `METRICS_TOKEN` (16 characters or more) on `/metrics` | `app.ts` |
| Dedicated install | Ed25519 license (`LICENSE_KEY`, `LICENSE_PUBLIC_KEY`), checked at start and daily against `/license/check` | `packages/persistence/src/license.ts` |

**Organization permissions.** Twenty permissions (for example `payments.view`, `review.decide`, `cashier.use`, `accounts.manage`, `developers.manage`, `data.manage`) in `apps/api/src/console/permissions.ts`. Built-in roles: admin (all), reviewer, operator, viewer. Organizations add up to 50 roles. Nobody can grant a permission they lack or change their own role. People can be limited to branches.

**Platform areas.** `PLATFORM_AREAS` in `apps/api/src/console/saas.ts` maps nine platform roles to areas such as `organizations`, `methods`, `billing`, `database` and `ops`. A platform owner can change the mapping except for owner, read and team.

## 6. Background and scheduled work

All background work runs in the worker (`apps/worker/src/service.ts`). Default intervals are in `apps/worker/src/context.ts`.

| Work | When | What it does |
| --- | --- | --- |
| Extract, OCR and provider runners | Continuous, leased jobs | One runner per stage and one per provider connector. Organizations take turns; batch jobs (priority 1) run after single payments |
| Connector sync | Every 30 seconds | Starts and stops provider runners as connectors change |
| Outbox | Continuous | Creates and sends webhook deliveries |
| Retention, archive and SaaS sweep | Every hour | Deletes evidence after retention (default 5 years), moves originals to the sealed archive after the hot period (default 90 days) |
| Push | Every minute | Empty Web Push notices for review and inbox counts |
| Escalation and automation | Every minute | Escalates overdue review cases; runs automation rules |
| Billing | Every minute | Marks paid invoices, settles store orders, sends Telegram order messages |
| Provider health | Every 5 minutes | Checks each connected bank's receipt address |
| Messages | Every 15 seconds | Sends email and SMS from the outbox |
| Heartbeat | Every 30 seconds | Reports the worker for the Operations page |
| Operations | Every minute | Alert checks, nightly backup after 02:00 Addis Ababa time (keeps 14), restore drills, purge of organizations past their 30 days in the trash |
| Export schedules | 06:00 Addis Ababa time | Scheduled CSV exports (decision 56) |

On the VPS, `cron` also runs `deploy/vps/backup.sh` at 02:45 server time (database dump, kept 14 days; weekly receipts archive, kept 35 days).

## 8. Deployment

| Topic | How it works |
| --- | --- |
| Where | Hostinger VPS (Ubuntu 24.04, Docker) shared with myseed.com.et, folder `/opt/transactionverify`, containers `tv-api`, `tv-worker`, `tv-migrate`, `tv-postgres`. Public address `https://transactionverify.myseed.com.et` through Myseed's Caddy on the shared `edge` network |
| How | From the control panel's Hostinger VPS page: `git archive` of the last commit is uploaded to `/opt/transactionverify/incoming`; `deploy/vps/deploy.sh <release>` builds the image, dumps the database, switches `current`, runs `tv-migrate`, starts API and worker, writes the Caddy site block and checks `/ready` and `/health` |
| Who can deploy | Whoever runs the control panel with the VPS SSH key and the encrypted panel settings. There is no CI deploy job |
| Roll back | `deploy.sh --rollback` starts the previous release (the newest three are kept). The database is not rolled back |
| Other commands | `deploy.sh --restart`, `deploy.sh --edge-check` |
| Optional hosts | Render blueprint (`render.yaml`, API web service and background worker, S3 storage, Supabase database), `autoDeploy: false` |
| Dedicated installs | Image `ghcr.io/<owner>/transaction-verify` published on a `v*` tag, plus a licensed install bundle from the platform |

## 9. Observability

- `GET /health` (status, deployment, contract version) and `GET /ready` (database reachable).
- `GET /metrics` in Prometheus text with a bearer `METRICS_TOKEN`.
- Worker alerts each minute: queue age (5 minutes), backlog (500), connector failure share, dead webhooks and messages, silent workers (2 minutes), connections (80 percent), backup age (26 hours). Each opens one row and notifies owners, operations and engineers once.
- Server errors: every 5xx writes a row to `server_errors` with the request ID; the console shows the request ID to the person.
- Public status page `/status` with five parts and incidents written by the platform team.
- Provider health checks every 5 minutes; three failures in a row marks a bank as down.
- Logs from Fastify (`LOG_LEVEL`) and worker logs per container, read from the control panel.

> [!WARNING]
> Alerts come from inside the worker. They cannot report the server being down. An outside monitor of `/health` and `/ready` is the operator's to set up (decision 63), and none is configured in this repository.
